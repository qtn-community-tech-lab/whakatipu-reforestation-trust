# Server agent instructions

These instructions apply to `server/` and its descendants. Read the relevant source and configuration before changing them. Keep changes focused and preserve unrelated work.

## Project scope

- [Backend specification](../planning/spec.md) is authoritative for the current planting-records release. HTTP contracts live in `../shared/api-types.ts`; import them through `@wrt/api-types` with `import type`.
- The `api` Supabase Edge Function implements the species, site, planting-area and planting-event routes. Authentication and hosted deployment are future work. Current requests can read and edit all active records, including unpublished ones.
- The migration from Supabase JS database access and API RPCs to Kysely is complete across all four resources and their 20 routes. The typed table representation, direct queries, transactions, centralized error handling and unreleased migration-file cleanup are finished. Treat the simplified Kysely implementation as the current baseline.
- Keep SQL constraints and indexes in versioned migrations. The API connects to Postgres with Kysely; its table representation is `supabase/functions/api/database.schema.ts`. The existing API migrations are unreleased, so James authorized editing them in place. Do not reset local data.
- Do not add future roles, authentication endpoints, public-view filtering, upload services, pagination, or import tooling unless requested.

## Implementation rules

- Keep the TypeScript direct and readable. Use Kysely query builders for database reads and writes, with small helpers for repeated rules. Avoid raw SQL except for simple Postgres expressions such as `now()` or transaction-local settings.
- Do not add repositories, generic CRUD frameworks, base classes, dependency-injection containers, validators, or runtime response schemas.
- Keep canonical HTTP response/request types in `shared/api-types.ts` and persistence types in `database.schema.ts`. Build response DTOs explicitly; never serialize whole rows.
- Assume HTTP bodies match their TypeScript contracts. Parse JSON directly; malformed JSON returns 400. Forward only documented editable fields. Database constraints remain the storage integrity boundary.
- Use one Kysely instance per isolate, the transaction-pooled `SUPABASE_DB_URL`, a one-connection Postgres.js pool, and `prepare: false`. Keep the pinned Deno dependencies and lockfile aligned. Do not use the Supabase JS database client or RPCs.
- Keep migrations focused on tables, constraints, indexes, RLS and grants. Do not add API SQL functions or composite RPC types. Preserve closed browser-role access; the server connection uses the Supabase-provided database URL.

## Database behavior

- Writes run inside `withTransaction`. Verify the active audit actor `usr_000000000001`; never accept audit identity from a request or create/reactivate the actor at startup. Use database timestamps and update audit fields on every mutation.
- Keep writes atomic in a transaction, without explicit row locks or lock-management queries. James requested straightforward reads and writes; concurrent edits use normal Postgres behavior. Keep detail GETs and their aggregates in a repeatable-read transaction.
- IDs remain opaque strings generated with `../_shared/ids.ts`. Site location IDs are generated by the server. Planting-area location IDs are supplied by the client and must be unused, including historical IDs. Planting-area parents are immutable.
- Event PUT replaces the complete species-count set. Keep existing line IDs and creation fields, generate IDs for new rows, soft-deactivate omitted lines, and reject line IDs owned by other events. Preserve inactive area/species references only in the cases already allowed by the specification. Species swaps must not violate the active-pair unique index.
- DELETE means soft deactivation. Repeated accessible deletes are idempotent and preserve the original deactivation time. Site deletion hides children without deactivating their historical rows.
- Keep calendar dates separate from timestamps. Postgres int8 quantities arrive as strings; sum with `BigInt` and reject totals above `Number.MAX_SAFE_INTEGER` before converting to JSON numbers.
- Preserve current visibility and summary rules: active rows only; areas require an active parent site; event summaries hide inactive areas; event details retain inactive area identity; event species IDs include positive active catalogue rows only; actual quantities still include inactive species. Keep histories ordered by date descending then ID descending and lists complete.

## Errors and logging

- Preserve HTTP statuses, reason strings, public messages and field guidance. `database.ts` catches query and transaction failures once and maps known Postgres codes; business checks throw `HttpError` directly. Preserve the original caught error as the cause, and never return raw database messages or hints. Do not retain RPC hint mappings or compatibility wrappers. Constraint/value errors return 400, known missing rows 404, conflicts 409 and unexpected errors 500.
- Keep `HttpError` causes. Do not swallow failed queries or turn them into empty collections or zero totals.
- Use `createRequestLog` and pass the request logger to resource functions. Every log line has the generated request ID, method, path, timestamp, level and event. Preserve operation start/completion, row counts, duration, stage and failure logs. Database transactions set the request ID in Postgres `application_name` for correlation.
- Never log credentials, request/response bodies, raw database messages/details, or unredacted URLs. Keep diagnostic stacks internal; `exceptionLogFields` omits messages and strips URL credentials, queries and fragments.
- Keep `X-Request-ID`, `Cache-Control: private, no-store`, CORS behavior, OPTIONS handling and the shared Hono error boundary intact.

## Runtime and checks

- The completed Kysely migration and simplification passed formatting, lint, TypeScript and diff checks. Regression tests were updated but not executed, and the revised migrations have not been applied as part of this work. Runtime/database verification remains pending; report it separately from the completed code migration.
- Keep `index.ts` as the small Hono handler export. `app.ts` owns routes and middleware; the resource modules own Kysely operations and DTO mapping; `database.ts` owns connection, transaction and database error boundaries; `database-helpers.ts` contains shared actor, stage and numeric helpers.
- Use strict TypeScript and explicit `.ts` relative imports. Prefer type-only imports where applicable. Avoid `any`, unchecked casts and compiler suppressions; explain unavoidable casts for Postgres' Point-only geometry constraint.
- From `server/`, run formatting, lint and type checks after code changes:

  ```sh
  deno fmt --check supabase/functions tests scripts ../shared ../planning/db-schema.ts
  deno lint --config supabase/functions/api/deno.json supabase/functions tests scripts ../shared ../planning/db-schema.ts
  deno task --config supabase/functions/api/deno.json check
  ```

- Do not run HTTP tests or reset/apply local database migrations unless James explicitly requests it. When asked to test, use the existing `deno task` targets and preserve all unrelated local data. Report exactly which checks ran and do not claim static checks establish runtime/database behavior.
