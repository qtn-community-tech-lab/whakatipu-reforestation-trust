The planting database

Every number WRT has recorded comes down to one sentence: this many plants of this species went to this part of a site in this season. The database is built around that sentence.

140,068 plants recorded5,449 lines360 planting events39 sites78 areas164 species23 seasons, Autumn 2015 to Autumn 2026
In short

  1. There are two layers. The old layer keeps the workbook data exactly as it came out. The new layer is the model the app uses, and it is built from the old one.

  2. History and new planting days share the same tables. A history event has a season but no date. A new event must have a date.

  3. Every history number can be traced back to the spreadsheet cell it came from.

  4. The whole design is written once, in TypeScript, with Drizzle. The database changes, the types and the form checks are all generated from that one place.

Two layers

The workbook is messy, and a third of its plants still wait on WRT rulings. So we keep it as it was and build a cleaner model on top. Nothing in the new layer replaces the old; it points back to it.

Old layer

  • Holds the five files the workbook was turned into, unchanged.
  • Only the import writes to it. Each import replaces it.
  • Staff can read it. The app's public API never sees it.

New layer

  • The model the app reads and staff edit.
  • Each import updates it without changing any ids.
  • New planting days go straight in, with no old row behind them.

The new model

Eleven tables, with one at the centre. A planting event is one area of a site in one season. Its lines say how many of each species went in. Everything else describes where, what, when, or what is still in question.

One day of planting, two ways

History and new data use the same two tables. The difference is what they know. The workbook recorded a season, a place and counts, but never a date or the kind of planting. A day staff record in the app knows all of these.

Every table

Open a table to see its columns. Green names are links to other tables; the yellow one is the link back to the old layer.

Every table staff edit also carries five columns not listed below: created_at, created_by, updated_at, updated_by and deactivated_at. The database fills in the first four. Rows are never deleted; setting deactivated_at retires them.

Rules, and where they live

Each rule sits as low as it can. The database enforces anything that must always be true, whatever writes the data. Zod repeats the rules a person filling in a form needs to see, so they get a clear message before anything is saved.

RuleKept by
A new event needs a date. A history event doesn't.Database check
Each species appears once per event.Database unique index
Quantities are whole numbers and never negative. An unknown count is empty.Database check
A site has at most one pin, and so does each area.Database unique indexes
A pin's area belongs to the pin's site.Database foreign key
An old row can't be deleted while a line points at it.Database foreign key
Who changed each row, and when.Database default and trigger
Rows are retired, never deleted.The deactivated_at column; access rules hide retired rows
The planting-day form: a real date, at least one species, each species once.Zod
The content files are well formed. CC BY photos credit their author.Zod, run by the import and the tests

Who sees what

Supabase's access rules (row level security) decide this inside the database, so every app and tool gets the same answer. Nobody is staff until an admin adds them, and sign-in is by invitation only.

WhoSeesCan change
Signed outPublished sites, areas, events and lines, and the species listNothing
Signed in, not staffThe same as signed outNothing
StaffEverything, including review topics and the old layerAnything in the new layer. Each change carries their name.

These rules apply to the browser, which talks to Supabase directly. Server code connects as the database owner, so it must check who is signed in before it writes.

Working with it

The design lives in one folder, db/schema/. Change it there and let the tools write the rest.

  1. Change the designEdit the tables in db/schema/.
  2. Generate the changenpm run db:generate writes a SQL migration. Read it before you run it.
  3. Apply itnpm run db:migrate runs it against the database.
  4. Refresh the historynpm run db:import rebuilds the old layer from the files and updates the new one.
A table, as it is written
export const plantingLines = pgTable("planting_lines", {
  id: integer().primaryKey().generatedAlwaysAsIdentity(),
  eventId: integer().notNull().references(() => plantingEvents.id),
  speciesId: integer().notNull().references(() => species.id),
  quantity: integer(),           // empty = unknown, never 0
  needsReview: boolean().notNull().default(false),
  legacyCode: text().unique()
    .references(() => plantingHistory.recordId),
  ...editTrail(),
}, (t) => [
  check("quantity_not_negative", sql`${t.quantity} >= 0`),
  ...staffAccess(),
]);
What the import promises
  • It runs in one go. Everything loads, or nothing does.
  • Ids stay the same from one import to the next.
  • What staff changed stays changed: pins, descriptions, rulings.
  • Pins, profiles and photos are added only if they are missing.
  • A site or area that loses all its history is listed, not deleted.

Not in it yet

None of these are in WRT's data today. Each can be added as new tables, without changing what is here, once WRT asks for it.

  • Survival and losses after planting.
  • Volunteers and the groups who planted.
  • Photos of plantings, as opposed to reference photos of species.
  • Drawn site boundaries, for when a pin and radius are not enough.
  • Nursery stock and seed lots.

Checked on Postgres 16 with the real data: every site, species and season total matches the current app; every line matches its old row; a second import keeps every id and every staff edit; the access rules and checks above all hold.
